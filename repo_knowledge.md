Codebase Understanding prompts AI Code Understanding Prompt Toolkit
A reusable set of prompts for understanding repositories, features, and code — especially code that AI has written for you. Copy any prompt into a conversation with Claude when you have repository access available. Every prompt is written to be teaching-oriented: it should explain WHAT was built, HOW it works, WHY it was built that way, and what you need to know before touching it.
How to use this toolkit: paste one prompt at a time, swap in the specifics (feature name, file path, error message, etc.) where noted in brackets, and treat the answer as a lesson, not just a report.

1. REPOSITORY & ARCHITECTURE
1.1 REPOSITORY ORIENTATION
Give me a guided tour of this repository as if I'm a new engineer joining the project today. Explain the overall purpose of the codebase, the main folders/modules and what each one is responsible for, and the primary languages, frameworks, and tools in use. Point out where the "core" logic lives versus configuration, infrastructure, and utility code. Do not change any code; this is purely for understanding.
1.2 PROJECT ARCHITECTURE
Explain the high-level architecture of this project: what are the major components/services/layers, and how do they communicate with each other? Describe the overall pattern being used (e.g. monolith, layered, microservices, MVC, event-driven) and why that pattern fits this project. Identify the entry points where execution begins for a typical request or process. Keep the explanation conceptual first, then ground it in real file/folder names from the repo.
1.3 TECH STACK & DEPENDENCIES
List the key dependencies, libraries, and frameworks this project relies on, and explain what role each major one plays. For the 3–5 most important dependencies, explain why a project like this would need them and what would break or become harder without them. Note any dependencies that seem unusual, outdated, or worth researching further. Do not modify any dependency files.
1.4 PROJECT SETUP & RUNTIME MODEL
Explain how this project actually runs: how it starts up, what processes exist, and how configuration/environment variables influence its behavior. Walk me through what happens from the moment the app is started to the moment it's ready to handle requests or perform its main job. Point out any build steps, background processes, or scheduled jobs I should know about. This is for understanding only — don't change any config or scripts.

2. FEATURE & MODULE
2.1 FEATURE UNDERSTANDING
Explain how [feature name] works from start to finish, including the main files, functions, components, and dependencies involved. Walk me through the execution flow in the order things actually happen. Explain why each important piece exists and how the pieces communicate with each other. Mention important assumptions, edge cases, and things I should understand before modifying this feature. Do not change any code; this is purely for understanding.
2.2 MODULE DEEP DIVE
Explain the purpose and internal structure of the [module/directory name] module. Describe what responsibilities it owns, what it exposes to the rest of the app (its public interface), and what it deliberately hides as internal detail. Identify which other modules depend on this one and which ones it depends on. Reference actual file and function names rather than speaking generically.
2.3 FEATURE BOUNDARIES
Help me understand exactly where [feature name] begins and ends in this codebase. Identify every file that is part of this feature versus files it merely touches in passing. Explain how I would know if a change I'm making is "inside" this feature or actually affecting something shared with other features. This will help me scope future changes safely without modifying anything now.
2.4 FULL FEATURE DEEP DIVE
Give me a comprehensive deep dive on [feature name] covering: what it does for the user, how it's implemented end-to-end (files, functions, data involved), why it was built this way, what alternative implementations existed, and what trade-offs were made. Also explain what could break if I modify it and what concepts I'd need to understand to build something similar myself. Treat this as the single most thorough explanation you'd give before I start working in this area.

3. CODE
3.1 FILE WALKTHROUGH
Walk me through the file [file path] line by line or section by section, in plain language. Explain what each major block of code is doing and why it's structured that way. Point out any non-obvious logic, clever tricks, or code that relies on assumptions I might not notice. Do not rewrite or refactor the file — this is purely a reading exercise.
3.2 FUNCTION/CLASS UNDERSTANDING
Explain what the function/class [name] does, including its inputs, outputs, and side effects. Describe the internal logic step by step and explain any non-obvious decisions, edge case handling, or assumptions baked into it. Tell me where in the codebase this function/class is called from and why it's needed there. Keep the explanation technically accurate but easy to follow.
3.3 CODE LOGIC BREAKDOWN
Break down the logic in [file/function/snippet] into plain-English steps, as if explaining an algorithm to someone learning to code. For any conditionals, loops, or recursive logic, explain what triggers each branch and why. Highlight any parts of the logic that are subtle, easy to misread, or likely to cause bugs if misunderstood.
3.4 NAMING & INTENT
Look at the names of the variables, functions, classes, and files in [area of code]. Explain what each name suggests about its intended purpose and whether the actual implementation matches that intent. Flag anything where the name is misleading, vague, or where the underlying behavior does more (or less) than the name implies.

4. FLOW & WORKFLOW
4.1 EXECUTION FLOW
Trace the execution flow for [action/feature/entry point], starting from the very first line of code that runs and ending at the final output or response. List each function/file involved in the order it actually executes, not the order it appears in the codebase. Note any branching points where execution could take a different path, and explain what determines which path is taken.
4.2 DATA FLOW
Trace how data moves through [feature/process], from where it originates (user input, database, external API, etc.) to where it ends up. Explain what transformations, validations, or mappings happen to the data at each step. Identify where the data is stored temporarily (variables, state, cache) versus persisted, and note anywhere the data's shape changes significantly.
4.3 API / REQUEST FLOW
Walk me through what happens to a request to [endpoint/route/action], from the moment it's received to the moment a response is sent back. Identify the routing, middleware, authentication/authorization checks, controller/handler logic, and any external calls involved, in the actual order they occur. Explain what happens differently on success versus failure/error paths.
4.4 DATABASE FLOW
Explain how [feature/operation] interacts with the database: which tables/collections are read from or written to, and in what order. Describe any queries, ORM calls, or transactions involved, and explain why they're structured that way (e.g. joins, indexes, batching). Note any places where data consistency, locking, or race conditions matter.
4.5 COMPONENT FLOW
Explain how the UI components involved in [feature/screen] are structured and how they communicate with each other (props, state, context, events, callbacks). Walk me through what happens from a user interaction to the resulting UI update, naming the actual components involved in order. Point out where state lives and why it was placed there rather than elsewhere.
4.6 DEPENDENCY MAP
For [feature/module/file], list everything it depends on (other internal modules, external libraries, environment variables, services) and everything that depends on it in return. Explain briefly why each dependency exists — what would be missing or broken without it. This should give me a clear picture of its "blast radius" in the codebase.

5. DESIGN & DECISIONS
5.1 DESIGN PATTERNS USED
Identify any design patterns (e.g. factory, singleton, observer, strategy, repository, dependency injection) used in [feature/module/file]. Explain how the pattern is implemented here specifically, referencing real code, and why this pattern fits the problem being solved. If no formal pattern is used, say so and describe the actual structure instead of forcing a label onto it.
5.2 WHY THIS APPROACH?
Explain why [feature/implementation] was likely built the way it is. Consider constraints such as the existing tech stack, performance needs, simplicity, team conventions, or the tools/libraries already in use. Be honest if the reasoning is unclear from the code alone, and say what additional context would help confirm the actual reasoning.
5.3 ALTERNATIVE APPROACHES
Describe two or three realistic alternative ways [feature/implementation] could have been built instead of the current approach. For each alternative, briefly explain how it would work and how it differs structurally from what exists now. Don't recommend rewriting anything — this is purely to broaden my understanding of the design space.
5.4 TRADE-OFFS
Analyze the trade-offs of the current implementation of [feature/approach]. Explain what this approach optimizes for (e.g. simplicity, performance, flexibility, speed of development) and what it sacrifices as a result. Compare it briefly against at least one alternative approach in terms of pros and cons, so I understand what was gained and given up.
5.5 ARCHITECTURAL DECISION REVIEW
Look at how [feature/system] is structured and evaluate it the way a senior engineer would in a design review. Point out what's well-designed, what's a reasonable-but-imperfect compromise, and what might be considered a design smell or technical debt. Explain your reasoning for each point rather than just labeling things good or bad.

6. DEBUGGING & MAINTENANCE
6.1 ERROR HANDLING REVIEW
Explain how errors and exceptions are handled in [feature/file/module]. Identify where errors are caught, logged, retried, or silently ignored, and explain what happens to the user or system in each case. Point out any places where error handling seems missing, too broad, or could hide real problems. Do not change any code — this is a review only.
6.2 SECURITY WALKTHROUGH
Review [feature/file/endpoint] from a security perspective. Explain what protections are already in place (e.g. input validation, authentication, authorization, sanitization, encryption) and where in the code they happen. Point out anything that looks like a potential vulnerability or an area worth double-checking, and explain the underlying security concept in simple terms.
6.3 PERFORMANCE ANALYSIS
Analyze [feature/function/query] for performance characteristics. Explain its time/space complexity or resource usage in plain terms, and identify any obvious bottlenecks such as repeated computation, unnecessary loops, N+1 queries, or blocking calls. Explain why these areas matter for performance and what generally causes that kind of issue, without rewriting the code.
6.4 TESTING COVERAGE & STRATEGY
Explain what tests exist for [feature/module/file], what kind they are (unit, integration, end-to-end), and what scenarios they actually cover. Identify any important cases — edge cases, error paths, or common usage patterns — that don't appear to be tested. Explain the overall testing strategy being used in this project so I understand the philosophy, not just the individual tests.
6.5 DEBUGGING GUIDE
Help me understand how I would debug [bug/error/unexpected behavior] in this codebase. Walk me through where to start looking, what logs, breakpoints, or tools would be useful, and how to trace the problem back to its root cause using the actual code structure. Explain your reasoning at each step so I learn the debugging approach, not just the answer.
6.6 REFACTORING READINESS
Before I refactor [feature/file/function], explain what I need to understand first: its current responsibilities, everything that depends on it, and any hidden behavior or edge cases a refactor could accidentally break. Suggest what to test or verify before and after refactoring to confirm nothing broke. Do not perform the refactor yourself — this is preparation only.
6.7 CHANGE IMPACT ANALYSIS
If I modify [file/function/feature], explain what else in the codebase could be affected, directly or indirectly. Identify callers, dependent modules, shared state, and any tests that would need to be re-checked. Rate the risk of this change as low/medium/high and explain your reasoning so I know how carefully to proceed.

7. LEARNING
7.1 UNDERSTANDING AI-GENERATED CODE
Explain the code you (or a prior AI session) just generated for [feature/file] as if I did not write it and need to fully understand it before trusting it. Break down what each part does, why it was likely chosen over alternatives, and flag anything unusual, overly clever, or worth double-checking. Assume I want to be able to explain and defend this code to another engineer afterward.
7.2 CONCEPTS I NEED TO LEARN
Based on [feature/file/technique] in this codebase, list the underlying concepts, patterns, or technologies I should understand to genuinely grasp how it works — not just what it does. For each concept, give a one- or two-sentence plain-language explanation and note whether it's something specific to this framework/language or a general software engineering idea worth learning properly.
7.3 LEARN TO BUILD IT MYSELF
Explain [feature] in a way that would prepare me to build something similar myself from scratch, without copying this exact code. Break the implementation down into the key steps and decisions involved, and explain the reasoning behind each one. Suggest what I should practice or learn first if I wanted to implement a simplified version of this on my own.
7.4 CONCEPT-TO-CODE MAPPING
Take the general concept of [e.g. "caching", "authentication", "pagination", "state management"] and show me exactly where and how it's implemented in this codebase. Connect the abstract concept to the concrete code so I can see the theory in practice. Note any ways this implementation is a simplified or non-standard version of the general concept.

8. AFTER AI BUILDS A FEATURE — RECOMMENDED PROMPT SEQUENCE
Use this sequence right after Claude (or any AI tool) finishes implementing a feature, so you build real understanding instead of just accepting the output.
1. 7.1 Understanding AI-Generated Code — get a full breakdown of what was just built before doing anything else.
2. 2.1 Feature Understanding — understand how the feature works end-to-end, in order of execution.
3. 4.1 Execution Flow and 4.2 Data Flow — trace exactly what happens and how data moves through it.
4. 4.6 Dependency Map — understand what this feature touches elsewhere in the app.
5. 5.2 Why This Approach? and 5.4 Trade-offs — understand the reasoning and what was sacrificed.
6. 6.1 Error Handling Review and 6.2 Security Walkthrough — sanity-check robustness and safety.
7. 6.4 Testing Coverage & Strategy — confirm what's actually tested versus assumed to work.
8. 6.7 Change Impact Analysis — understand what you'd risk before modifying anything.
9. 7.2 Concepts I Need to Learn — close any knowledge gaps the feature exposed.
10. 7.3 Learn to Build It Myself — cement the learning so you could reproduce it independently.
